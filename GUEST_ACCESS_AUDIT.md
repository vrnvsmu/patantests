# TestPatan: аудит гостевого доступа и подготовленные исправления

## Краткий вывод

Проект — статическая GitHub Pages страница. Она загружает `@neondatabase/neon-js@0.9.0-beta` с CDN и оборачивает Neon Auth/Data API в клиент-совместимый интерфейс. Отдельно в `functions/timewebs3.ts` реализованы HTTP endpoint для загрузки/удаления в Timeweb S3 и маршрут `/guest-rpc`, который ходит в PostgreSQL через `pg` и серверный `DATABASE_URL`.

Гостевые обращения к `list_topics`, `start_attempt`, `check_answer`, `finish_attempt`, `get_attempt_review` уже направлялись на `/guest-rpc`, но обычное публичное чтение не было последовательно переведено туда: например `turntable_sets`, `site_content`, `notifications`, `learning_materials` и `question_options` в отдельных страницах инициализировались прямыми запросами Neon Data API. Именно поэтому одних GRANT на таблицы недостаточно, когда Data API не видит JWT и отвечает `PGRST302`.

Путь URL `https://br-noisy-rain-bg4das6a-timewebs3.compute.c-9.eu-central-1.aws.neon.tech/` буквально прописан в `index.html` и назначен как base URL и для guest RPC, и для административной записи объектов. Он указывает на Neon compute-домен по форме адреса; файл `.neon` называет Neon project и ветку `test`. `functions/timewebs3.ts` совпадает с маршрутом `/guest-rpc`, а также реализует загрузку/удаление S3. Однако в локальной копии нет манифеста/скрипта деплоя, поэтому сам факт актуального развертывания файла на этом URL из репозитория доказать нельзя. Имена переменных окружения handler (`DATABASE_URL`, `TIMEWEB_S3_*`, `NEON_AUTH_*`, `ALLOWED_ORIGIN`) показывают его ожидаемую конфигурацию, не доказывают, что она есть на удалённом сервисе.

## Потоки

При загрузке страницы Neon SDK инициализируется по `AUTH_URL` и `DATA_API_URL`. `sb.auth.getSession()` и `loadMe()` обслуживают зарегистрированного пользователя; затем темы загружаются напрямую из `topics` только если есть загруженный профиль, иначе вызывается `guestRpc('list_topics')`. Старт теста, ответ, завершение, разбор и продолжение гостевой попытки маршрутизируются через `appRpc` к тому же compute endpoint. Вход пользователя обрабатывается Neon Auth/SDK, профиль и личная статистика остаются в Data API с JWT и RLS.

Макро/микро-картинки отдаются браузеру прямыми публичными URL Timeweb S3 (`s3.twcstorage.ru`). 360° кадры тоже читаются из S3; список `frame_paths` приходит из `turntable_sets`. Административная запись/удаление файлов идёт через тот же compute endpoint, но отдельным методом и под Bearer JWT администратора, после чего handler использует AWS SDK к S3. S3 не исполняет TypeScript.

## Причины по операциям

Получение общедоступного контента: отдельные страницы инициализировали часть таблиц напрямую через Data API без JWT; публичные SQL-права сами по себе не устраняют ошибку gateway-аутентификации.

Создание попытки: route уже использует gateway и SECURITY DEFINER функцию. В исходной схеме `user_id IS NULL` означал общую идентичность всех гостей. Зная UUID можно было пытаться адресовать чужую гостевую попытку. Новая миграция добавляет hash случайного browser-session token и отдельные функции, сверяющие hash при каждом изменении/чтении попытки.

Проверка, завершение и разбор: новые SQL-процедуры проверяют, что попытка принадлежит гостевому токену, и возвращают только результат этой попытки. Correct answer/explanation по-прежнему не читаются гостевым клиентом из `question_answers` напрямую.

Персональная статистика: должна оставаться только у авторизованного пользователя. Профили, избранное и `attempts` читаются в профиле после `needLogin()` и через Data API JWT/RLS. Гостевой endpoint не имеет операций для чтения профилей/статистики/избранного.

## Изменения в папке

`index.html`: гостевой Data API чтения для материалов, оформления, уведомлений, 360° метаданных и вариантов ответа перенаправлены на узкие guest RPC; создаётся случайный токен сессии браузера, передаваемый только в guest route; гостевой токен сохраняется в локальном состоянии попытки для продолжения в этом браузере; authenticated пути оставлены через существующий SDK.

`functions/timewebs3.ts`: allowlist гостевых операций дополнена только публичными чтениями; body валидируется, для попыток обязателен токен, есть rate limit и сериализация мутирующих операций в рамках экземпляра; обращения к контенту идут через специально созданные ограниченные SQL-функции. Обработчик S3 и JWT/admin-check не менялись по назначению.

`sql/0009_guest_api.sql`: добавляет поле hash гостевого session token, отдельные функции start/check/finish/review/resume и узкие функции чтения публичных данных; создаёт NOLOGIN роль `testpatan_guest_api` с минимальными правами, отзывает прямой анонимный доступ к таблицам и не выдаёт Data API ролям EXECUTE на гостевые процедуры. Handler использует новое обязательное серверное окружение `GUEST_DATABASE_URL`; оно должно соединяться отдельным DB login-пользователем, которому администратор Neon даст членство в `testpatan_guest_api`. Секрет не публикуется в JavaScript.

## Неподтверждённые инфраструктурные факты / что нужно сделать перед релизом

В этой сессии не было доступа к внешним Neon endpoint, SQL Editor, журналам сервиса или deploy-панели. Поэтому не подтверждены состояние ветки Neon `test`, актуальная роль подключения compute, фактическое наличие сервиса на URL, допустимые CORS origins, фактическая версия установленного SDK по документации, фактическая работа S3 и реальное выполнение сценариев в браузере.

Не выкладывайте этот архив как законченный production hotfix. Сначала проверьте deploy target handler-а. Если endpoint управляется Neon Compute, убедитесь, что репозиторий/проект функции действительно развернут туда, и что серверный `GUEST_DATABASE_URL` указывает на Neon ветку `test`; S3 secrets должны остаться только server-side. Если выяснится, что сервиса нет/он старый, ни имя домена, ни файл в `functions/` не создают runtime автоматически — нужен deploy через поддерживаемый способ запуска Neon compute-функции либо отдельный уже используемый серверный runtime.

SQL migration применять только в Neon SQL Editor при выбранной ветке `test`, после проверки прав/extension и экспортной резервной копии. Не запускать целиком dump `01_neon_public_migration_fixed.sql` повторно. Для безопасной проверки сначала выяснить фактическую роль DB handler-а и владельца функций, затем проверить `has_table_privilege('anonymous','public.attempts','SELECT')` (ожидается false) и тестовые guest-функции через handler. После создания роли `testpatan_guest_api` grant EXECUTE уже настроен только для этой роли; перед deploy проверьте, что DB login, заданный через `GUEST_DATABASE_URL`, имеет членство в ней. Не выдавать EXECUTE anon/authenticated и не давать anon SELECT на таблицы.

## Тесты

Локально извлечены все три inline JS блока из `index.html`; `node --check` прошёл. Проверены целостность ZIP и отсутствие в нём `.git`/`node_modules`. Установленные npm зависимости доступны: `@neondatabase/neon-js` не указан в package.json, так как SDK загружается с CDN, а функции используют `pg`, `jose`, `@aws-sdk/client-s3`.

Полная TypeScript typecheck не пройдена: в проекте отсутствуют `@types/node` и `@types/pg`; это ограничение имеющейся конфигурации, не доказательство корректности или некорректности runtime. SQL не выполнялся на Neon, DB-интеграционные тесты и сценарии браузера не запускались.

Обязательная ручная проверка после миграции и deploy: главная без входа; список тем; макро- и микроматериалы с изображениями; 360° набор; теория; старт экзамена; ответ; завершение и разбор; обновление/продолжение в той же вкладке; вход старого пользователя и его профиль/история; попытка гостя прочитать UUID чужой попытки с другим токеном (должна быть отказана); проверка, что гость не читает Data API `attempts/profiles`; административная загрузка и удаление картинки в S3; чтение файлов напрямую из S3.
