# Сводка проекта TestPatan (ВГМУ) для нового ИИ-агента

**Дата подготовки:** 26 октября 2026 г.\
**Назначение:** этот документ нужно прикрепить вместе с ZIP-архивом
проекта в новый чат. Он фиксирует архитектуру, известные нюансы и
единственную актуальную нерешённую проблему.

## 1. Проект в двух словах

TestPatan --- сайт для прохождения тестов по патологической анатомии для
ВГМУ. Сайт опубликован на GitHub Pages:

-   Публичный сайт: https://vrnvsmu.github.io/patantests/
-   Репозиторий и рабочие файлы проекта нужно проверять по
    прикреплённому ZIP-архиву. Не предполагать, что локальные патчи уже
    опубликованы в GitHub.
-   Backend и база данных --- Supabase.
-   Основная клиентская логика находится в `index.html` (одностраничный
    сайт с JavaScript).
-   Изменения frontend обычно передаются пользователю готовым файлом
    `index.html` для замены в репозитории. Изменения базы --- отдельным
    SQL-файлом/миграцией для ручного запуска в Supabase SQL Editor.

**Важно для нового агента:** сначала изучи фактическое содержимое ZIP,
особенно актуальный `index.html`, SQL-миграции и вызовы Supabase. Не
считай все предыдущие патчи уже установленными: пользователь заменял
файлы и запускал SQL вручную, но агент не имеет подтверждения, что
каждый отдельный файл/скрипт был применён. Не заявляй, что что-либо
опубликовано или выполнено в Supabase, если это не было проверено.

## 2. Технологии и схема работы

-   Frontend: HTML/CSS/JavaScript в `index.html`.
-   Хостинг: GitHub Pages.
-   Backend: Supabase (Postgres + RPC-функции).
-   Авторизация и пользовательский контекст используют Supabase Auth
    (`auth.uid()`).
-   Пользователь обычно хочет получить конкретный исправленный файл для
    скачивания, а не только фрагменты кода. Не проси повторно загрузить
    архив, если он уже доступен в текущем разговоре; в новом чате ZIP
    будет приложен пользователем.

Типичный цикл изменений: 1. Изучить ZIP и найти точный участок
кода/миграцию. 2. Исправить причину, а не маскировать ошибку
отображения. 3. Проверить синтаксис JS (например, извлечь inline-скрипт
и прогнать `node --check`) и SQL-логику. 4. Передать готовый файл с
рабочей ссылкой. 5. Для SQL явно указать, что его нужно запустить в
Supabase → SQL Editor, если агент действительно не имеет подключения для
применения миграции. 6. Не утверждать, что исправление работает в
продакшене, пока пользователь не проверил его или пока это не
подтверждено доступными инструментами.

## 3. Основные таблицы Supabase

По ранее просмотренной схеме известны следующие таблицы/поля
(обязательно перепроверь по ZIP и текущей базе, если есть доступ):

### `public.attempts`

Известные поля: - `id` - `user_id` - `mode` - `topic_id` -
`question_count` - `correct_count` - `percent` - `duration_seconds` -
`created_at` - `status` - `finished_at`

**Особенность `percent`:** при попытке исправить завершение марафона
появилась ошибка: `column "percent" can only be updated to DEFAULT`

Это означает, что в текущей схеме `percent` ведёт себя как
генерируемый/вычисляемый столбец и его нельзя напрямую присваивать в
`UPDATE`. Нельзя писать `SET percent = ...`, пока схема не проверена.
Впоследствии марафон был исправлен и сейчас пользователь подтверждает,
что результаты марафона показываются корректно. Не ломать это
исправление и не возвращать ручное обновление `percent`.

### `public.attempt_answers`

Известные поля: - `id` - `attempt_id` - `question_id` -
`chosen_option_id` - `is_correct` - `answered_at`

Записи связывают вопрос с попыткой и содержат выбранный вариант и
признак правильности.

### `public.question_answers`

Известные поля: - `question_id` - `correct_option_id` - `explanation`

### `public.questions`

Известные поля включают: - `id` - `topic_id` - `section` - `prompt` -
`image_path` - `is_published` - и другие.

В таблице `questions` `topic_id` используется для статистики по темам.
RPC `start_attempt` раньше возвращал объект вопроса без `topic_id`,
поэтому в итогах марафона frontend дополнительно запрашивал
`questions(id, topic_id)` по ID вопросов.

### `public.topics`

Ранее виденная структура включала `block`, `title`, `sort_order`,
уникальность по `(block, title)`. Перепроверить по архиву/миграциям.

## 4. Важные RPC-функции

Названия и сигнатуры, ранее виденные в базе. Перед правкой сверить с
актуальными SQL-миграциями/реальной схемой.

### `start_attempt(p_mode text, p_topic_id bigint default null, p_count integer default 10)`

-   Допустимые режимы ранее включали `macro`, `micro`, `theory`, `exam`.
-   При запуске выбирает опубликованные вопросы с данными ответа.
-   Группирует вопросы с одинаковым `image_path` и перемешивает группы.
    Поэтому фактическое количество вопросов может отличаться от
    запрошенного `p_count`, если выборка организована по группам
    изображений.
-   Создаёт записи в `attempt_answers` с `chosen_option_id = NULL`.
-   Ранее возвращаемые JSON-объекты вопросов не включали `topic_id`.

### `check_answer(p_attempt uuid, p_question uuid, p_option uuid)`

-   Проверяет, что попытка ещё выполняется.
-   Проверяет, что вариант ответа принадлежит данному вопросу.
-   Находит правильный вариант, вычисляет корректность и записывает
    `chosen_option_id`, `is_correct`, `answered_at` в `attempt_answers`.
-   Ранее обновляла строку только при `answered_at IS NULL`. Поэтому
    повторная отправка уже записанного ответа может не перезаписать его.
-   Учитывает владельца попытки/авторизацию. Если frontend восстановил
    попытку не в том пользовательском контексте, это может мешать
    сохранению ответов.

### `finish_attempt(p_attempt uuid)`

-   Завершает попытку и записывает итоговые данные.
-   Изначальная версия считала правильные ответы, но не обновляла
    `percent`, что давало устаревшее/пустое значение.
-   Попытка вручную обновлять `percent` привела к ошибке
    `column "percent" can only be updated to DEFAULT`.
-   **Текущее состояние:** пользователь сообщил, что проблема завершения
    марафона теперь решена и марафон корректно показывает результаты. Не
    менять эту функцию без изучения действующего SQL и без сохранения
    работающего поведения.
-   Перед любой правкой учесть, что `percent` может быть вычисляемым
    столбцом. Считать `correct_count`/ответы источником истины и не
    обновлять `percent` вручную, если реальная схема не доказывает
    обратное.

### `get_attempt_review(p_attempt uuid)`

-   Возвращает JSON с вопросами попытки, выбранными вариантами,
    корректностью, правильными вариантами и объяснениями.
-   Для марафона frontend использовал список review, чтобы посчитать
    сводку по темам.

## 5. Режим марафона --- уже исправлен, не регрессировать

Пользователь подтвердил: **по марафону вопросов больше нет, результаты
отображаются корректно**.

Требуемое поведение: - По завершении марафона показывается сводка по
темам. - Не показывается подробный разбор каждого отдельного вопроса. -
Для сводки нужны `topic_id` вопросов; поскольку `start_attempt` не
включал `topic_id` в возвращаемый JSON, frontend ранее дополнительно
получал `questions(id, topic_id)` по ID вопросов. - Не удалять эту
логику без проверки. - Недавно была ошибка при завершении:
`column "percent" can only be updated to DEFAULT`. После последующих
исправлений пользователь подтвердил, что результаты марафона корректны.
Это закрытая проблема, не текущая задача.

## 6. ЕДИНСТВЕННАЯ ТЕКУЩАЯ ПРОБЛЕМА: «Последние результаты» на главной странице всегда показывает 0 решённых вопросов

### Симптом

В блоке «Последние результаты» на главной странице число решённых
вопросов отображается как `0`, хотя пользователь реально отвечает на
вопросы.

При этом: - Кнопка **«Продолжить с последнего задания» работает
правильно**. - Сайт возвращает пользователя к тому вопросу, на котором
он остановился. - Ранее решённые вопросы в восстановленной попытке тоже
визуально помечены как решённые. - В марафоне итоговые результаты уже
отображаются правильно. - Предыдущие попытки изменить подсчёт «Последних
результатов» не помогли: пользователь сообщил, что после последнего
исправления там ничего не изменилось.

Это значит, что состояние/ответы для восстановления, вероятно, доступны
frontend хотя бы частично, но блок «Последние результаты» получает
статистику неправильным способом, читает не те поля/строки, сталкивается
с ошибкой запроса или показывает не ту величину. Это гипотезы, не
установленная причина. Не делай вывод, что ответы отсутствуют в базе,
пока это не проверено.

### Что уже пробовали

В одной из предыдущих версий `index.html` функция `loadLatestResults()`
была изменена так, чтобы: 1. Запросить последние попытки из `attempts`
по `user_id`, отсортировать по `created_at`, взять до 6 записей. 2.
Запросить `attempt_answers` по найденным `attempt_id`, выбрав
`attempt_id, chosen_option_id, is_correct`. 3. Посчитать answered как
количество строк с `chosen_option_id`, а correct --- количество строк с
`is_correct === true`. 4. Рассчитать процент на frontend как
`correct / question_count * 100`, а не доверять `attempts.percent`.

Однако пользователь подтвердил, что видимое поведение не изменилось.
Следовательно, нельзя просто повторить ту же правку. Нужно выяснить,
почему запрос/подсчёт не отражается в UI.

В одной из тех версий был fallback:

``` js
st=answerStats[a.id]||{answered:0,correct:Number(a.correct_count||0)}
shownCorrect=st.answered?st.correct:Number(a.correct_count||0)
pct=Number(a.question_count)?100*shownCorrect/Number(a.question_count):0
```

Это тоже может скрывать проблему, а счётчик в UI мог обозначать не число
правильных ответов, а число решённых вопросов. Не предполагай смысл
числа без проверки разметки и функции отрисовки.

### Ранее наблюдавшиеся данные

Пользователь ранее показывал запрос к попыткам с колонками:
`id,status,question_count,correct_count,answered_count,actual_correct_count`

Некоторые результаты: - finished, `question_count=396`,
`correct_count=1`, `answered_count=11`, `actual_correct_count=1` -
finished, `question_count=396`, `correct_count=0`, `answered_count=0`,
`actual_correct_count=0` - finished, `question_count=3`,
`correct_count=0`, `answered_count=2`, `actual_correct_count=0` -
finished, `question_count=5`, `correct_count=3`, `answered_count=3`,
`actual_correct_count=3` - были и другие попытки с нулём ответов.

Эти данные исторические и не доказывают состояние нынешней попытки.
Также `answered_count` и `actual_correct_count` могли быть вычисляемыми
выражениями в SQL-запросе, а не реальными полями `attempts`.
